# hc-1159 首页 Start 输入框 ⌘V 访达里复制的视频文件（验收记录）

分支 `claude/hc-1159-start-paste-copied-file`，叠在 hc-1158（`claude/hc-1158-paste-copied-file` `205c2012`）上。

单线程模式关着、业务工作台开着（默认）时，首页是 Start 页：一个「业务目标」输入框，不是聊天输入框。hc-1158 让聊天输入框收 ⌘V 的复制文件，这个页面还不收：拖进来的视频会成为附件，⌘V 什么都不发生。原因是 Start 页背后没有挂聊天输入框（首次打开时根本没挂；开过一次对话后挂着但隐藏），hc-1158 的粘贴路径和窗口级粘贴（paste-to-focus）的总线都到不了 Start 的附件草稿。

## 改了什么

`use-chat-file-drops.ts` 里加一个窗口级、捕获阶段的 paste 监听。它只在首页拖放生效的那个条件下挂上：Start 页拥有草稿（聊天输入框没露出来）、网关连着、没有在跑的回合。复制来的条目走首页拖放同一条路（`onAttachDroppedItems`，全部条目），所以：

- 输入框有焦点时 ⌘V，和焦点在页面上（点了标题、空白处）时 ⌘V，都成为附件；后一种把焦点放回输入框。
- 文件夹成为附件列表里的文件夹卡片，和拖进来一样（不会变成隐藏输入框里的 `@folder:` 引用）。
- 带路径的图片文件也收：Start 没有自己的图片粘贴，拖进来的图片在这里会附上。新增 `copiedEntriesInClipboard`（含图片），`copiedFilesInClipboard` 改为在它上面去掉图片，行为不变。
- 不收的：没有路径的 File（截图、浏览器里复制的图片）、纯文字、别的输入框里的粘贴、对话框/菜单盖着时、Start 不是当前输入框时（分屏里另一个会话的输入框刚有过焦点）、抽屉盖在 Start 上（这时聊天输入框露出来，走 hc-1158 的路）。

一次粘贴只附一次：捕获阶段先于窗口级粘贴（冒泡阶段）运行，消费掉的事件到不了 composer 总线，所以聊天输入框挂没挂着都只有这一处附上。

## 怎么跑的

`e2e/start-paste-copied-file.spec.ts`，和 hc-1158 的 `paste-copied-file.spec.ts` 同一套：开发版 Electron（这个分支 `npm run build` 的 dist）、从这个检出起的真实引擎（`hermes serve`）、按脚本回答的本地假模型、全新沙盒，**不设** `APEXNODES_SINGLE_THREAD`（单线程关）。登录页点「使用自己的密钥」接到假模型，没有任何付费调用。

1. 主进程 `clipboard.writeBuffer('public.file-url', …)` 放进 `口播第一条.webm`（hc-1158 核对过，这样粘贴交出的 File 和访达复制的一样）。点「业务目标」输入框，按 ⌘V：出现视频附件，上方是「转逐字稿 / 拆它为什么火 / 仿写成我的脚本 / 复刻成我的」，输入框里没有文字。
2. 放进 `口播第二条.webm`，点页面标题（规格核对过焦点不在任何输入框上），按 ⌘V：第二条也成为附件（共两个），四个按钮还在，焦点回到输入框。
3. 点「转逐字稿」：发出的请求带着两条视频（假模型收到的提示里两个文件名都在），回答出现。这时聊天输入框已挂上。
4. ⌘N 回到 Start（聊天输入框挂着、隐藏），点页面标题，放进 `口播第三条.webm`，按 ⌘V：第三条只出现一个附件，附件数 = 粘贴前 + 1。

规格结束时写回运行前剪贴板里的文字、HTML 和 RTF；本机跑的时候另外在前后整份存取了剪贴板，跑完核对过原内容还在。

复现：

```bash
cd apps/desktop && npm run build
HC1159_SHOTS="$TMPDIR/hc1159" npx playwright test e2e/start-paste-copied-file.spec.ts --workers=1
```

本机跑之前按 e2e 惯例临时关掉 `apexnodes://` 协议注册（不提交）；跑完核对过 `apexnodes` 的处理程序仍是 `com.apexnodes.desktop`。

## 改动前后

同一份规格在 hc-1158 的头（没有这次改动）上构建后跑：第 1 步失败，按钮组是空的（`Expected ['转逐字稿', …] / Received []`），输入框里没有附件，也没有文字（`00-before-paste-does-nothing.jpg`）。在这个分支上整份通过（15 秒）。

单元测试 `use-chat-file-drops-paste.test.tsx`（真的 Start 页 + 真的 `useChatFileDrops` + 真的 `attachDroppedItems`，窗口上按 use-keybinds 的方式挂着 paste-to-focus）的反向验证，每处注入先断言命中 1 次（R2 是 2 次：注册和注销），跑完原样恢复：

| 撤掉什么 | 哪些变红 |
|---|---|
| R1 不挂 Start 的 paste 监听 | 7/13：输入框里粘贴（两种剪贴板）、页面上粘贴、和拖放交出同样的条目、文件夹、图片、聊天输入框挂着时在输入框里粘贴 |
| R2 改成冒泡阶段（排在 paste-to-focus 后面） | 1/13：页面上粘贴（paste-to-focus 先消费，首次打开没人收） |
| R3 不 `preventDefault` | 3/13：输入框里粘贴两种（事件没被消费）、聊天输入框挂着时页面上粘贴（附了两次） |
| R4 别的输入框里的粘贴也收 | 1/13：别的输入框 |
| R5 不收图片 | 1/13：图片 |
| R6 附上后不放回焦点 | 1/13：页面上粘贴 |
| R7 抽屉盖着时也收 | 1/13：抽屉 |

## 顺带看到的（不是这次的改动，拖放一样）

用同一套环境把视频**拖**到 Start 上再点「转逐字稿」核对过，两件事和粘贴无关：

- 从 Start 发出时，每个附件在 `<HERMES_HOME>/attachments/` 里被暂存两次（`口播第一条.webm` 和 `口播第一条-2.webm`），提示里引用的是 `-2` 那份。规格因此按文件名主干匹配提示。
- 发出后 ⌘N 回到 Start，刚发出去的附件又出现在 Start 的草稿里（截图 04 里的前两条）。

## 没在这里验的

- 真的在访达里按 ⌘C：没有访达的操作权限，用的是同样形状的剪贴板（见 hc-1158 的实测表）。
- 一次复制几个文件：Chromium 只交出第一个，这里不处理。
- 右键菜单的「粘贴」：它调 `webContents.paste()`，应当触发同一个 paste 事件；读代码得出，没有实测。
- Start 上粘贴截图（没有路径的图片）、在 Start 页面上粘贴文字：仍走原来的路（输入框里截图不收；页面上的文字经 paste-to-focus 交给主输入框，首次打开没人收，挂着时进隐藏的输入框）。读代码得出，不在这次范围，见 PR 的出口清单。
- 单线程模式开着：首页是聊天输入框，由 hc-1158 负责；这次的监听只在 Start 拥有草稿时挂上。
- 打包产物、Windows、真实账号和模型：都没用。
