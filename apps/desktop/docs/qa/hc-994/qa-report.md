## 1. 用户看到什么

### 粘贴即识别

- 在聊天输入框或首页输入框里粘贴抖音、小红书、视频号、快手、哔哩哔哩的链接（包括 App 复制出来的整段分享文案、短链、没写 `https://` 的手打链接），输入框上方出现三个胶囊：「转逐字稿」「拆它为什么火」「仿写成我的脚本」。
- 拖进本地视频（MP4、MOV、M4V、WebM、MKV、AVI、FLV，和桌面端视频分析认的格式一致），或用「+ › 添加文件或视频」选进来，同样出现这三个胶囊。
- 点一个胶囊就发出一句预设请求，例如「把这条抖音视频转成逐字稿：https://v.douyin.com/iRNBho6u/」。分享文案里「复制打开抖音…」这类 App 自带的话不带进去；用户在粘贴之外自己打的字另起一行跟在后面，不会丢。
- 不想用就照常打字发送。胶囊跟着链接走：链接还在输入框里就一直在，发出去或删掉链接就消失，没有关闭按钮（和旁边的建议胶囊一样）。
- 请求只用现有工具和技能：`social_download` / `media_transcribe`、`video-script-breakdown`、`douyin-video-transcript`。不新增任何后端接口。

### 顺手修的现成问题：聚焦粘贴的链接不变引用（待 Kael 审的行为变化）

`resolveExactLinkPaste` 用全局正则 `URL_RE.exec` 判断「是不是只粘了一个链接」，之后 `lastIndex` 停在那个链接后面；同一次粘贴紧接着的 `linkifyUrls` 用 `matchAll` 从这个位置往后扫，于是聚焦粘贴时第一个链接从不变成 `@url:` 引用，而且这个状态是全局的，上一次粘贴会影响下一次。没聚焦时 ⌘V、手打链接按空格都会变引用，三条路不一致。

本 PR 在 `linkifyUrls` 开头把 `lastIndex` 归零。结果：普通链接聚焦粘贴后会稳定变成 `@url:` 引用（发送前网关会抓取网页，这本来就是这条路的设计，⌘V 和手打一直如此）；短视频链接不受影响，仍是纯文本。Kael 10-20 定了：普通链接保持网页引用。

第二轮顺手修的边界：原来 `URL_RE` 只在空白、引号、方括号处结束，「看这个https://example.com/post/1，写得好」整段（含「，写得好」）都进了引用，发送前网关拿着这个错链接去抓网页。现在 `URL_RE` 和 `TYPED_URL_RE` 在全角标点、弯引号、省略号和紧贴的汉字处结束；汉字紧跟在 `/ = ? # &` 后面时算路径或参数，留在链接里。孪生出口：`linkifyUrls`（聚焦粘贴、⌘V、编辑已发送消息）、`chipTypedUrlOnSpace`（手打按空格；紧贴汉字时不做引用，留原文）、`resolveExactLinkPaste`（「只粘了一个链接」时给选中文字加超链接：带「，」的不再算单个链接）。检查过没改：`app/artifacts/artifact-utils.ts` 自己的 `URL_RE`（产物面板找链接，不在输入框，不做引用）。代价：链接里直接写着汉字、而这个汉字前面不是 `/ = ? # &` 的（例如 `/文章-标题` 会在「标」前断开），引用会短一截；浏览器地址栏复制出来的链接是 `%E4…` 编码，不受影响。
